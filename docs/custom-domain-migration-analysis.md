# Миграция Atlas: старые URL и варианты без прерывания

Состояние исследования: 30 октября 2026. Рабочая основа: `fresll/pgt-mt-atlas`, `main` a108f0ac20d4a8a4f0d11c6f6ac821c1bfc76fcd. Никакие DNS, Pages или публикация не изменялись. Старый URL `https://fresll.github.io/pgt-mt-atlas/ru/science/embryo-concordance/?atlas_redirect_check=1` ответил HTTP 200 без перенаправления; `atlas.mazunin.science` на момент проверки не разрешался. Это исходное состояние, а не эксперимент после назначения домена.

## Что известно о старых ссылках

- Текущий Pages — проектный сайт: GitHub обслуживает префикс `/pgt-mt-atlas/`, а браузер открывает статические языковые файлы под ним. Custom domain задаётся конкретному Pages-сайту, а доменная маршрутизация и потенциальные перенаправления с `github.io` контролируются GitHub, не DNS зоны mazunin.science. Из DNS нового домена нельзя настроить HTTP-правила на `fresll.github.io`.
- [Документация GitHub](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages) описывает домены и отдельно говорит о перенаправлениях между apex и www; в ней не найдено гарантии преобразования всех старых project URL в новые с удалением префикса, сохранением пути и query. [Открытый вопрос сообщества](https://github.com/orgs/community/discussions/197790) именно об этом не содержит проверенного ответа. Нельзя утверждать, что перенаправления нет, либо обещать, что оно всегда корректно.
- Возможны различные результаты: 3xx на правильный `/ru/.../`, ошибочный `/pgt-mt-atlas/ru/.../` или корень, ответ 200 со старым содержимым, 404 или ошибка TLS/DNS. Сервер не видит `#fragment`: браузер может сохранить или заменить его по правилам redirect, поэтому надо проверить в браузере. Проверять query в сетевом ответе, файлы и варианты без конечного `/` отдельно. Постоянный 301 может кэшироваться браузерами и затруднить откат.
- `404.html`, meta refresh или JavaScript в проектном артефакте не гарантируют вмешательства в redirect, выполняемый до отдачи артефакта GitHub; 404-обходы не дают настоящего HTTP 3xx и ненадёжны для поисковиков, клиентов без JS и загрузок. Публикация отдельного проекта на том же старом адресе не гарантирована без отдельного подтверждённого эксперимента с маршрутизацией.

## Варианты

1. **Прямой Custom domain на существующем Pages** — сохраняется исходное требование одного репозитория и GitHub Pages, но безопасное поведение старых глубоких ссылок до переключения не доказано. Настройка Pages, DNS, новый артефакт и TLS не атомарны, возможен перерыв. Ветка содержит подготовленный workflow именно этого варианта. Сначала провести отдельный контролируемый эксперимент на другом project Pages с временным поддоменом, идентичной структурой, Actions и 404, затем всё равно проверить реальный Atlas при переключении; эксперимент снижает неопределённость, но не гарантирует поведение Atlas.
2. **Рекомендуемый для непрерывности: два независимых Pages-сайта.** Оставить `fresll/pgt-mt-atlas` Pages и старый URL без изменений. Создать отдельный проект GitHub Pages, обслуживающий корневую сборку того же зафиксированного коммита из существующего исходного репозитория, и назначить домен только второму проекту. У GitHub Pages один сайт на репозиторий, поэтому для второго потребуется отдельный репозиторий *публикационных артефактов* или отдельная поддерживаемая инфраструктура; научные исходники остаются в `fresll/pgt-mt-atlas`, не в репозитории главной страницы. Проверить на отдельном проекте и аккаунте фактическую возможность привязки домена, CI, HTTPS и все маршруты. Прежние ссылки продолжают открывать прежний сайт, а не автоматически перенаправляться; это сохранение доступности, не перенос SEO-сигналов через HTTP 301. Обеспечить обновление двух сборок из одного проверенного SHA, мониторинг и проверку совпадения научных данных. Это снижает риск, но не гарантирует отсутствие любого сбоя провайдера или DNS.
3. **Альтернатива: второй статический хост**, например [Cloudflare Pages](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/), подключённый к тому же GitHub-репозиторию или получающий готовый артефакт. Исходный GitHub Pages остаётся неизменным. Это смена хостинга нового домена, новый сервис и операционная зависимость; требует отдельного согласования пользователя. Для субдомена провайдер требует сначала связать домен с проектом, затем настроить CNAME ([документация](https://developers.cloudflare.com/pages/configuration/custom-domains/)). Проверить 404, слеши, MIME, загрузки, TLS и лимиты; HTML по маршрутам обслуживается согласно [документации](https://developers.cloudflare.com/pages/configuration/serving-pages/). Никакой провайдер не может управлять HTTP-ответом домена `fresll.github.io`.

У параллельных сайтов появляется дублирование индексируемого контента. Не менять canonical действующего сайта на неподготовленный домен: после проверки нового сайта отдельно согласовать политику поисковой индексации, sitemap и canonical на обеих копиях. Новый экземпляр до готовности сделать закрытым или noindex; проверить, что preview не индексируется. Старый сайт со старым canonical не станет автоматически перенаправлять. Ссылки на обновляемые данные могут со временем расходиться, если не выпускать две сборки из одного SHA.

## Рекомендуемый порядок после отдельного разрешения

1. Зафиксировать текущий commit, адреса, состояние Pages, конфигурацию DNS, срок действия/доступность сертификата и артефакт действующего сайта; подготовить владельца и критерии остановки. Проверить выборку старых URL и downloads, затем сохранить список всех 110 путей из sitemap и контрольные суммы файлов данных.
2. Подготовить второй Pages-проект и механизм публикации артефакта *из того же исходного репозитория*. Не направлять на него существующий GitHub Pages и не включать deployment существующего проекта. Подготовленный здесь `deploy-pages.yml` требует переработки под две независимые публикации: слияние его как есть запустит прямое переключение на существующем Pages. Новый workflow должен сохранять действующие ETL, научные и браузерные проверки, явно строить оба base и привязывать оба результата к одному SHA. Не допускать автоматической публикации непроверенных веток.
3. Развернуть закрытый или noindex preview без назначения публичного домена; проверить все 110 путей, CSS/JS, изображения, загрузки, Plotly, язык, мобильную и RTL версии, счётчик, 404, query/hash и конечные слеши; сверить данные и ответы со старым сайтом. Проверить настройки GoatCounter и CORS на реальном origin. Включение индексации и canonical отложить до готовности целевого адреса.
4. Только после дополнительного согласования владельца подготовить домен у выбранного хоста, проверить владение и HTTPS, затем настроить соответствующий DNS. Для GitHub Pages сначала назначают custom domain сайту, затем настраивают DNS; соблюдать [порядок GitHub](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site). Дождаться TLS и DNS. Старый проект Pages не менять.
5. Перед открытием индексации снова проверить все 110 прямых URL на новом домене и все 110 старых URL, файлы и query/hash, реальные данные счётчика; следить за журналами и ошибками, повторить проверки из нескольких сетей. На старом домене в параллельном варианте ожидается работоспособный ответ 200, а не redirect; поэтому скрипт `check-legacy-redirects.py` предназначен **только** для варианта прямого перенаправления. После проверки отдельно согласовать canonical и поисковую миграцию. Любой переход на redirect со старого сайта требует отдельной реализации и проверки, без предположения о серверном 301 на GitHub Pages.
6. Откат при ошибке: прекратить распространение нового адреса и индексацию; восстановить предыдущую запись DNS и конфигурацию нового хоста из зафиксированного состояния, если она менялась, соблюдая защиту от захвата домена. Старый Pages в параллельной схеме продолжает работать; вновь проверить его реальные URL, графики и файлы. Учесть кэш DNS и поисковиков, поэтому время отката не гарантировано. Не удалять старое развёртывание до отдельного решения и достаточного периода наблюдения.

При прямом варианте после назначения домена запустить из `site` на полной публичной сборке `python3 scripts/check-legacy-redirects.py`. Он требует реальный 3xx и точный конечный URL для всех 110 страниц с query. Проверить в браузере `#fragment`, отсутствие слеша и файлы. При провале восстановить исходный Pages domain/base, прежний артефакт и DNS; проверить старый сайт из чистого клиента, учитывая потенциальный кэш 301. Прямой вариант невозможно честно назвать гарантированно беспрерывным.
