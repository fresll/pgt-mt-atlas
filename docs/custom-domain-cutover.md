# PGT-mt Atlas: подготовка перехода на atlas.mazunin.science

Локальная ветка готовит сборку к корню собственного домена; до переключения её нельзя публиковать. Исторические отчёты и старые ссылки в них намеренно оставлены как записи о прежних публикациях. `ATLAS_BASE=/` и `ATLAS_CANONICAL_BASE=https://atlas.mazunin.science/` задаются в производственной сборке; `ATLAS_BASE=/pgt-mt-atlas/` сохраняется для тестирования прежнего размещения. Файл CNAME в артефакт не добавляется: источник публикации — GitHub Actions, настройку домена выполняет владелец в Pages.

## Важно: эта инструкция описывает прямое переключение

Более безопасный вариант — параллельное размещение с сохранением действующего GitHub Pages. Сравнение, условия и порядок см. в [анализе миграции](custom-domain-migration-analysis.md). Данный workflow переключает существующий Pages и **не подходит без переработки** для параллельной схемы.

## Порядок прямого переключения после отдельного подтверждения владельца

1. Зафиксировать текущие настройки Pages/DNS и последний успешный артефакт, проверить доступ к откату. Проверить владение доменом в GitHub; подготовить у DNS-провайдера CNAME `atlas` → `fresll.github.io` без пути репозитория. Сначала назначить домен в настройках Pages, затем применить DNS. Следовать [инструкции GitHub](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site); дождаться проверки DNS и HTTPS, включить HTTPS при доступности. Эти изменения могут временно сделать сайт недоступным.
2. Согласовать окно переключения: текущий workflow публикует только main. После подтверждения перенести подготовленные изменения в main и запустить workflow, согласовав порядок с настройкой Pages/DNS. Дождаться окончания всех научных, технических и послепубликационных проверок. Проверить Pages deployment URL: workflow намеренно требует точного нового URL и завершится ошибкой, если настройки ещё не готовы.
3. Проверить реальные HTTPS-адреса всех языков, прямой вход, перезагрузку и ссылки на файлы; протестировать графики, переключатель языка и посещения (в том числе доступ счётчика в браузере без блокировщика). Старые и новые пути в аналитике различаются: исторические разбивки по путям не объединяются автоматически, общий счётчик остаётся тем же. Проверить правила разрешённых доменов/фильтрации в GoatCounter, если новые визиты не отражаются.
4. Из `site` выполнить `python3 scripts/check-legacy-redirects.py` на полной публичной сборке. Проверка обходит все 110 старых URL, требует настоящую цепочку HTTP 3xx и точный новый путь с query; также вручную открыть несколько старых ссылок с `#якорем` в браузере и проверить сохранение якоря. Дополнительно проверить ссылки на конкретные скачиваемые файлы, варианты без завершающего слеша и ссылки, известные извне. Ответ 200 со старого адреса, неверный путь, ошибка TLS или потеря query — провал проверки, а не подтверждение перенаправления. До переключения реальный результат неизвестен.
5. Если проверка не прошла, остановить переключение и восстановить прежнюю конфигурацию и артефакт; затем повторно проверить старые адреса. GitHub Pages не даёт гарантии произвольных правил перенаправления на старом project URL; отдельная публикация редиректов на этом URL может конфликтовать с маршрутизацией Pages и требует доказанной схемы на стороне контролирующего `fresll.github.io` сайта/хостинга. Не обещать сохранение ссылок до её проверки. Если независимый перенаправляющий хост недоступен, согласовать другой план до повторного переключения.

Проверки локальной сборки: `npm ci`, `npm test`, стандартные e2e с прежним base, публичные e2e, `python3 scripts/audit-indexing.py` и `npx playwright test --config playwright.domain.config.ts` на корневой публичной сборке. В workflow сохранены проверка ETL и научные тесты, существующие браузерные проверки и проверка после публикации. Внешний CORS для чтения счётчика проверяется с новым Origin перед публикацией; это не доказывает приём новых посещений или настройки на стороне GoatCounter.
